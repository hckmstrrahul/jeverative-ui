jeverative / architecture

One library.
Two ways to compose.

Jev-only arranges configurable prepared elements. Jev + LLM uses Jev for the layout and a text model for prompt-specific content. Both render through the same styled component system.

Jev chooses; the library defines the possibilities.

Content comes from prepared samples or supplied data. Jev cannot invent arbitrary components or unrestricted copy. Unsupported requests fail explicitly, without silently switching to a text model.

Plan the page. Generate its content.

Jev directs the page structure; a text model chooses registered components and writes the content inside it.

Correction is conditional: local fixes run first. If needed and auto-fix is enabled, the same text model gets one targeted repair attempt. Jev is not called again. An invalid result cannot replace the saved completed screen.

More flexible content, with more generation work.

The text model uses registered components; it does not create new React implementations. Jev + LLM’s API identifier is hybrid. There is no silent model upgrade or engine fallback.

The shared foundation

  • React and shadcn/ui adapters render validated documents.
  • Styling is applied to typography, colors, spacing and icons.
  • Desktop, tablet and mobile constraints shape the canvas.
  • Local state supports prototype controls and registered interactions.
  • Curated reference rules guide composition; Mobbin is not queried during generation.

What to measure

Compare completion, relevance, layout, interactions, latency and cost per usable screen. Jev-only avoids text generation but has narrower content coverage. Jev + LLM adds text-token costs and possible correction latency. Missing usage data is not zero cost.

Current playground modes: Jev-only and Jev + LLM. No generated JavaScript is executed. Sample data and local actions are prototypes, not live business integrations. The preview timer reports server duration, excluding browser rendering and network overhead.
